## 🔴 Critical bugs (fix before launch)

### 1. Jargon Lookup is silently broken for every user

**Location:** `frontend/src/hooks/useReadingStore.ts:304-312` + `frontend/src/components/reading/AiGuidancePanel.tsx:165-176`

**What's supposed to happen:** Student types a confusing term in the input box on the AI Guidance panel, clicks the button, sees an explanation.

**What actually happens:**
- Input field stores typed term in local state `jargonTerm` (`AiGuidancePanel.tsx:165`).
- Button click calls `lookupJargon()` with no arguments (`AiGuidancePanel.tsx:176`).
- `lookupJargon` in the store **always sends `term: ""`** to the backend (`useReadingStore.ts:312`).
- Backend asks Gemini "what does '' mean in this paper?" → returns junk or refuses.
- The user never sees the explanation they wanted.

**Why the tests don't catch it:** Playwright mocks the response to `/sessions/.../jargon` to return a pre-baked explanation, so the test passes regardless of what's in the request body. The bug is in **what the frontend sends**, not in what the backend does — and no test checks the request body for this endpoint.

**Fix:** `lookupJargon` needs to accept the term and pass it through. About 6 lines of code in `useReadingStore.ts` and `AiGuidancePanel.tsx`.

### 2. `/superpowers/recommendations` queries columns that don't exist

**Location:** `backend/routers/superpowers.py:365-409`

**What's supposed to happen:** Self-study page shows "Recommended for You" cards based on what the student has read.

**What actually happens:** The route does:
```python
db.from_("papers").select("id, title, authors, year_published, category").eq("is_self_study", True)
```
None of `is_self_study`, `authors`, `year_published`, `category` exist in `supabase/migrations/20260329000000_initial_schema.sql`. PostgREST will return an error response. The endpoint will return `{"error": "..."}` (or possibly a 200 with `data=None` due to the way `db.py:execute` swallows errors), and the recommendations panel will be empty or show a runtime error.

**Why the tests don't catch it:** No backend test exercises this endpoint, and the Playwright mock fakes the response.

**Fix options:**
- (a) Write a migration adding `is_self_study`, `category`, `authors`, `year_published` columns to `papers`. The frontend assumes they exist.
- (b) Rewrite `get_recommendations` to use only columns that exist (`id`, `title`, `created_at`) and serve "newest 3 self-study papers" with a different heuristic.

Option (a) is more honest to the original design intent. Option (b) is faster.

### 3. Recommended-paper "Start" button calls `/library/fetch` with wrong shape

**Location:** `frontend/src/pages/student/SelfStudyPage.tsx:159`

**What's supposed to happen:** Student clicks "Start" on a recommended paper card, gets routed into the reading session for that paper.

**What actually happens:**
```ts
await api.post("/library/fetch", { paper_id: paperId });
```
But the backend's `FetchCoreRequest` (`backend/schemas/library.py`) requires:
```python
core_id: str
title: str
```
There's no `paper_id` field — Pydantic will reject the request with **422 Unprocessable Entity**. The button does nothing.

**Why the tests don't catch it:** The Playwright mock for `/library/fetch` returns a fake success response no matter what the request body is. Backend pytest never tests this exact body shape.

**Fix:** Wrong endpoint. Recommended papers are already in the DB — they don't need fetching. The button should either:
- Call `POST /sessions/` directly with the existing assignment_id (if the recommendation includes one), or
- Add a new endpoint `POST /library/start/{paper_id}` that creates a self-study session for an existing library paper.

## 🟠 Other issues found

### 4. `/library/categories` always returns `[]`

**Location:** `backend/routers/library.py:264-266`

The route handler is a stub that returns an empty list. Frontend `SelfStudyPage.tsx:61` calls it and binds the result to a category dropdown. The dropdown will always be empty.

**Fix:** Either implement the categories aggregation (depends on adding the `category` column from issue #2), or remove the dropdown from the UI.

### 5. `/library/fetch` duplicate-detection is dead code

**Location:** `backend/routers/library.py:198-203`

```python
existing = await db.from_("papers").select("id, title").eq("core_id", body.core_id).single().execute()
```

`core_id` doesn't exist on `papers`. This query will error, `existing.data` will be `None`, and the duplicate-detection branch is silently skipped. Every `/library/fetch` call re-downloads from CORE and creates a new paper row. Wastes Gemini quota; creates duplicate library entries.

**Fix:** Either add `core_id` column to `papers` (linked to issue #2) or remove the duplicate-detection block.

### 6. `/library/upload` accepts `category` form field but ignores it

**Location:** `backend/routers/library.py:64-66`

```python
category: str = Form(default=""),
```

The handler accepts it but never uses it (no `category` in the insert payload). Same root cause as the other `category` issues.

## What "tested" means in this report

- **✅ status** = I traced the code, ran the test, and the test exercises the realistic path. You can trust these in production.
- **🟡 status** = I confirmed the code is consistent and the test suite passes, but the test uses mocks. Real Supabase / Gemini / CORE could behave differently. Run the manual smoke test to convert these to ✅.
- **🔴 status** = I traced the code and proved it cannot work, regardless of what tests say.
- **⚪ status** = The code exists but I couldn't find a code path that calls it.

The tests are **not lying** — they correctly verify the function-level contracts. They just don't catch when the *contracts disagree with each other* (frontend sends `paper_id`, backend expects `core_id`) or when the *code disagrees with the schema* (`is_self_study` doesn't exist).

This kind of bug only gets caught by either: (a) integration tests against a real DB, or (b) the kind of static cross-reference I just did.
